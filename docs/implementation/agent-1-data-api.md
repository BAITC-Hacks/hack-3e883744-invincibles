# Агент 1 — синтетический кит, ядро, API и запуск

Обязательное чтение: [ТЗ ШАГРА](../superpowers/specs/2026-09-23-shagra-design.md), особенно §4–7, §9–13, §15–17. Это самостоятельное задание в составе ТЗ, а не разрешение изменить его требования.

**Цель:** предоставить двум другим агентам стабильный контракт, а пользователю — корректное хранение, импорт, изменение навыков и запуск. **Лимит:** 300 минут вместе с интеграцией; новые функции после 240-й минуты не добавлять.

## Владение

backend/app/contracts, core, data, application, http, bootstrap.py, main.py; backend/tests/core и api; Python зависимости и настройка Python path; tools/generate_kit.py, tools/validate_kit.py; data/synthetic; contracts; Dockerfile, compose.yaml, .env.example, .gitignore; docs/DATA.md. Не редактировать recommendations и frontend, README принадлежит А3.

## Поставки и критерии

### A1.1. Контракт и ядро — первые 60 минут

- [ ] В первые 20 минут создать типы из §9 и HTTP-примеры из §10: profile-active, profile-no-next-grade, recommendations-llm, recommendations-fallback, preview, completion, hr-overview, import-valid, import-invalid, error-stale.
- [ ] На примерах использовать E0001, EV_BACKEND_01, версии employee=1/dataset=1; история пустая. Значения preview получать по формуле, а не вручную подбирать ради UI.
- [ ] Опубликовать коммит контракта А2/А3. Все примеры валидировать Pydantic-моделями.
- [ ] Реализовать пять функций core из §9.2. Проверить эталон 66.7→83.3, cap ниже текущего, неизвестный навык, no_next_grade, target_met.
- [ ] Создать SQLite schema, Repository и короткие транзакции; выполнить тест на уникальность completed для пары.

Доказательство: `python -m pytest backend/tests/core -q`; все тесты проходят, core не импортирует HTTP/БД/LLM.

### A1.2. Качественный кит — 60–120 минут

- [ ] Реализовать seeded-генератор по §6, включая все восемь фиксированных сотрудников; резерв входит в общие количества.
- [ ] Названия 60 навыков и 40 событий сделать предметными; русские/английские имена — явный словарь. Для HR не нужны реальные ФИО.
- [ ] Исторические completed применить к базовому состоянию один раз при генерации; экспортировать конечный snapshot.
- [ ] Написать валидатор и README кита с полной схемой и provenance.
- [ ] Дважды сгенерировать во временные каталоги; сравнить хеши четырёх файлов и manifest.
- [ ] Проверить counts=200/40/60, 24 месяца, все внешние ссылки, долю >=70% активных целевых профилей с кандидатом.

Доказательство: generate_kit и validate_kit проходят; повторная генерация побайтово совпадает. Сгенерированный кит не называется официальным.

### A1.3. API и записи — до 180 минут

- [ ] Реализовать вход/выход, серверные роли и Origin-проверку. Employee не может читать чужой профиль; HR имеет заданные полномочия.
- [ ] Profile/preview/completion: preview не пишет БД; completion использует одну транзакцию, версии и Idempotency-Key.
- [ ] Проверить retry с тем же ключом после изменения версии; он возвращает сохранённый успех. Новый ключ для completed даёт 409.
- [ ] Реализовать HR-срез на одном read snapshot без вызовов LLM.
- [ ] Validate/commit импорта: оба файла, атомарность, сохранение нормализованного payload, повторное применение/no-op, просрочка и конфликт версии.
- [ ] Подключить RecommendationService А2 и проверки версии перед/после await; никогда не удерживать write transaction во время AI.

Доказательство: `python -m pytest backend/tests/api -q`, сценарии Q10–Q15/Q17/Q18; битый последний CSV-row ничего не меняет.

### A1.4. Воспроизводимость — 180–240 минут

- [ ] Multi-stage Dockerfile собирает UI А3 и API; app раздаёт их с одного origin.
- [ ] Compose запускает app/ollama/model-init; загрузка модели не блокирует чтение профиля.
- [ ] При пустой БД импортировать кит; при рестарте не перезаписывать snapshot, историю и секрет.
- [ ] Экспортировать contracts/openapi.json; проверить совпадение runtime схемы и examples.
- [ ] Передать А3 точные проверенные команды, env, порт, версии образов и troubleshooting для README.

Доказательство: чистый `docker compose up --build`, login/profile, затем completion и restart с сохранением нового состояния.

## Интеграционные зависимости

От А2 нужен класс RecommendationService с интерфейсом §9.3 и реальный статус endpoint. От А3 нужен frontend build в dist. До их готовности backend можно проверять FakeProvider и временной статической страницей в тестах; в финальной сборке подмена запрещена.

Официальный кит при появлении: прочитать README организаторов, реализовать отдельный адаптер с тестовым образцом. Если формат получить невозможно, зафиксировать, что совместимость не проверена; не тратить время на эвристическое угадывание полей.

## Передача

А3 получает команды запуска и env; А2 — актуальные контракты и реализацию core. Отчёт включает пройденные тесты, сохранность после рестарта, повторяемость кита и незакрытые внешние зависимости. Не объявлять весь MVP готовым только по готовности API.
